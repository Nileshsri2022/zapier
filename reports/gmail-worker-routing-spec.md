> **One-sentence summary:** today Gmail-triggered Zaps bypass the queue and execute inside `apps/server` through a limited inline executor — and the audit below shows the Gmail push ingress in front of it is independently broken in three places. This spec fixes the whole chain: verified ingress → hydrate → dedup → `ZapRun + ZapRunOutbox` → worker, then deletes the inline executor.

## 1. Context — audit findings (verified 2026-10-19, all reproducible from cited files)

### 1.1 Two execution engines exist; Gmail uses the wrong one

|                                 | Worker engine (all other triggers)                                                                     | Server inline executor (Gmail)                                                                                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Path                            | `ZapRun + ZapRunOutbox` → processor drains → Kafka `zap-events` → `apps/worker` stage-by-stage         | Gmail webhook handler _is_ the executor: a `for` loop inside the API-server request; `ZapRun` written **after** execution with the final status                                                                                                               |
| Code                            | `apps/worker/src/index.ts` (`executeActionWithRetry`, `processMessage`)                                | `GmailWebhookController` → `GmailTriggersController.processGmailTrigger` → `ZapController.processGmailTrigger` (l.347) → `executeZapActions` (l.285) → `ActionsController.executeAction`                                                                      |
| Actions                         | `Email`, `Solana`, `WhatsApp`, `Telegram`, `Webhook` (registry `apps/worker/src/utils/actionTypes.ts`) | `Email` (SMTP via nodemailer), `Solana` (**placeholder — only `console.log`s, sends nothing**, `ActionsController` l.72–92), `GmailSend/GmailReply/GmailAddLabel/GmailRemoveLabel/GmailMarkRead/GmailArchive`; anything else throws `Unsupported action type` |
| Chaining / conditions / retries | `stepOutputs` + `{previousOutput.…}`, `stepConditions`, `filterConditions`, 3× retry, failure email    | **None** — each action gets the raw payload, return values are discarded (l.293), no retry, errors only join into `ZapRun.errorMessage`                                                                                                                       |
| Templating                      | `replaceKeys`: `{nested.key}`                                                                          | `replacePlaceholders`: `{{flat_key}}` only (`ActionsController` l.92)                                                                                                                                                                                         |
| Email action transport          | Resend (`sendEmailWithTextBody`, text body, body templated, **subject not templated**)                 | SMTP (`SMTP_HOST/USER/PASS`, **HTML body**, `to`/`subject`/`body` all templated)                                                                                                                                                                              |

Consequences already user-visible today: Gmail → WhatsApp/Telegram/Webhook Zaps always fail; Gmail → Solana Zaps record `completed` while sending nothing; Gmail → AI (roadmap) is impossible. Gmail → Email appears to work, which is why this stayed hidden. (One other caller shares the inline executor: the legacy `POST /api/triggers/webhook/:zapId` in `TriggerController.handleWebhook` — disposition in §4.7. The primary webhook ingress in `apps/hooks` already goes to the worker per F2.)

### 1.2 The Gmail push ingress in front of it is broken in three further, independent places

As written, it cannot be shown that a single real Gmail push notification has ever executed a Zap. Each break below alone stops the flow:

| #                                                      | Break                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Evidence                                                                                                                                                                  |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B1 — Auth rejects real Pub/Sub**                     | `handleGmailWebhook` requires an `x-goog-signature` HMAC-SHA256 header and **fails closed** (401) without it. Gmail `users.watch` publishes to a Cloud Pub/Sub **topic** (`GmailService.watchEmails`, topic from `GMAIL_PUBSUB_TOPIC`, whose default in `.env.example` is still the placeholder `projects/your-project/topics/gmail-notifications`); Pub/Sub push subscriptions authenticate with an **OIDC JWT bearer token**, never an `x-goog-signature` HMAC. Nothing in the repo transforms Pub/Sub messages into this endpoint's expected format                                                                                                                                                              | `apps/server/src/controllers/GmailWebhookController.ts` (`verifyGmailWebhookSignature`, l.180+), `apps/server/src/services/GmailService.ts` l.89–121, `.env.example` l.12 |
| **B2 — Payload schema Gmail never sends**              | The handler decodes the Pub/Sub envelope, then switches on `notificationData.eventType` (`new_email`, `label_added`, …) plus `messageId`/`labelIds`. Real Gmail watch notifications contain exactly `{ emailAddress, historyId }` — no `eventType`, no `messageId` — so every real notification would land in `default: "Unhandled Gmail notification type"` and return 200 having done nothing. Identifying _which_ messages changed requires a `history.list` delta call that exists nowhere (`GmailWatch` state is modeled in the schema but only written, never read for history processing; `renewGmailWatch` is a TODO stub, so watches would also expire after 7 days)                                       | `GmailWebhookController.ts` l.14–23, l.53–78, l.203+; `packages/db/prisma/schema.prisma` (`GmailWatch`)                                                                   |
| **B3 — Fan-out joins on a key that matches zero rows** | Handlers call `processGmailTrigger(data.emailAddress, …)`, whose first query is `gmailTrigger.findMany({ where: { serverId } })`. But `GmailTrigger.serverId` stores the **`GmailServer.id` uuid** (validated as such in `createGmailTrigger`), while `emailAddress` is `"someone@gmail.com"` — and `GmailServer` has **no email column** to join on. The OAuth callback even fetches the profile (which includes the address) and discards it, storing `name: name \|\| 'Gmail Server'`. Result: fan-out finds zero triggers, silently                                                                                                                                                                             | `GmailTriggersController.ts` l.6–12, l.96–148; `GmailController.ts` l.88–104; `schema.prisma` (`GmailServer`: no email field)                                             |
| **B4 — Empty payload; most filters unpassable**        | Even if B1–B3 were fixed, the handlers forward only `{ id, threadId, eventType, timestamp }` (+`labelIds`/`starred`) — **no `from`, `subject`, `snippet`, `body`, or `labels`**. `shouldTrigger` filters on exactly those absent fields (`senderFilter`/`subjectFilter` read `emailData.from`/`.subject`; labeled/starred/moved read `emailData.labels`, but ingress sends `labelIds`): every labeled/starred/moved/sender/subject-filtered trigger evaluates `false`, and any downstream step (Email body, AI input) receives no email content at all. `GmailService.getEmailMetadata()` exists to hydrate a message but is never called here — `GmailTriggersController` imports `GmailService` and never uses it | `GmailWebhookController.ts` l.92–163; `GmailTriggersController.ts` l.3, l.26–97; `GmailService.ts` l.169–206                                                              |

Smaller debris in the same area: two different functions are both named `processGmailTrigger` (`GmailTriggersController` serverId→fan-out vs `ZapController` zapId→execute, imported under alias `runZapActions`), and `TriggerController.handleGmailTrigger` is exported but mounted on no route (dead).

### 1.3 What already exists to build on (no new patterns needed)

- **Transactional outbox** is the established hand-off: `CronRoutes` (F6) and `GitHubRoutes` create `ZapRun` + `ZapRunOutbox`; `apps/processor` drains up to 50 per `/process` call to Kafka. Note the drain filters `zap.isActive: true` — a run queued for an inactive Zap would sit in the outbox forever, so this spec checks `isActive` **before** creating rows (preserving `ZapController.processGmailTrigger`'s current inactive-Zap semantics).
- **Dedup** (F1): `apps/hooks/src/dedup.ts` — Redis `SET NX PX`, 24 h TTL, fail-open with warning. `apps/server` already depends on `@repo/redis`.
- **Gmail access**: `GmailService` (per-server OAuth credentials, `GmailRateLimiter`, `GmailErrorHandler.executeWithRetry`, `getEmailMetadata`, `getNewEmails`, `watchEmails`); `googleapis` is a server dependency (transitively provides `google-auth-library` for OIDC verification).
- **Test infrastructure**: `apps/server/tests/setup.ts` already mocks `zapRun`, `zapRunOutbox`, `gmailServer`, `gmailTrigger`; `tests/zaps/run-status.test.ts` pins the _intent_ "run status is recorded honestly, and the webhook still returns 200" — that intent must survive the migration (§7).
- **Precedent for risky-Zap handling**: `apps/server/src/seed.ts` deactivates armed Zaps that reference unimplemented/dead trigger/action types and logs their IDs instead of silently letting them misbehave (used for legacy Email/Solana triggers and Gmail catalog actions, F4).

## 2. Goals & non-goals

### Goals

- **G1 — Single execution engine:** Gmail-triggered Zaps execute only in `apps/worker`, through `ZapRun + ZapRunOutbox` → processor → Kafka, gaining the full action catalog, retries, `filterConditions`/`stepConditions`, `stepOutputs` chaining, and failure notifications. This is what unblocks `AI Transform` (email summarization) for Gmail.
- **G2 — A Gmail ingress that works with real Gmail:** verified Pub/Sub push auth, `history.list` delta processing with a stored cursor, watch renewal — or, if the §8 P1 probe shows the GCP infrastructure doesn't exist, the polling variant (§4.5). Ingress choice is a gated decision (D2), the routing core is ingress-agnostic.
- **G3 — One stable, hydrated payload contract** for `ZapRun.metadata` (§4.3): `from`, `subject`, `snippet`, `body`, `labels`, IDs, dates — so templates (`{subject}`), filters, and future AI inputs (`{subject}\n\n{body}`) actually have content. Existing `shouldTrigger` filter semantics are preserved, just evaluated on hydrated data.
- **G4 — No duplicate runs from redelivery:** mandatory dedup per Zap+message+event before any rows are created (matters twice over once Solana becomes real).
- **G5 — Safe migration, nothing turns on by surprise:** pre-flight audit of every Gmail-triggered Zap in the production DB; Solana (fake→real) and `Gmail*` (→ worker-unsupported) Zaps **deactivated pending conscious owner re-enable**; `{{…}}` Email templates rewritten to `{…}` via dry-run-reviewed script; env kill-switch to roll back routing during rollout.
- **G6 — Delete the inline executor when done** (`executeZapActions`, server `executeAction`, placeholder Solana, dual templating) after its last caller (legacy server webhook route) is migrated — completing D1 rather than leaving a third copy to drift.

### Non-goals

- Worker implementations of `GmailSend`/`GmailReply`/label actions (the F4-removed catalog entries). `GmailActionsController`/`GmailAction` disposition is a follow-up (§10); this spec only ensures deleting the inline executor doesn't silently delete intended API surface without an explicit decision.
- Gmail OAuth/server-management UX, Gmail dashboard pages (`apps/web/app/gmail`), trigger-creation APIs (`POST /api/gmail/triggers` CRUD stays as-is).
- Attachment content/bytes in the payload (only `hasAttachments` boolean); full-mailbox backfill/history replay on first connect (cursor starts at "now", §4.4).
- Changing processor drain behavior, Kafka topics, worker dispatch, or `evaluateFilters`/`replaceKeys` semantics (except the Email-subject templating line, D8).
- Editor changes: Gmail triggers in the Zap editor keep working exactly as configured today; no new editor surface.

## 4. Design

### 4.1 Target flow

```
Gmail watch ──► Pub/Sub topic ──► push ──► POST /api/gmail/webhook        (§4.4, if push wins D2)
                                              │  verify OIDC JWT → decode {emailAddress, historyId}
                                              │  resolve GmailServer(s) by email (D3)
                                              │  history.list since lastHistoryId → changed messages + event kinds
        ┌─────────────────────────────────────┘
        │  (polling variant §4.5 converges here with server + messageId + eventType)
        ▼
dispatchGmailEvent(server, messageId, eventType)                          (§4.2)
   hydrate once (GmailService: metadata + body)  ── fail ──► 500, provider redelivers, no rows written
   for each GmailTrigger of server, zap included:
       zap.isActive?  shouldTrigger(hydrated)?  dedup claim (D5)?
       └─► $transaction: ZapRun{pending, metadata: §4.3 payload} + ZapRunOutbox
        ▼
processor /process ──► Kafka zap-events {zapRunId, stage:1} ──► apps/worker (unchanged)
```

The webhook always ACKs 200 once rows are durably written (preserves the `run-status.test.ts` "providers must not retry and double-run" intent); it returns 500 only when _nothing_ was written and a provider redelivery is therefore both safe (dedup claims precede writes per Zap) and desirable (transient Gmail-API failure during hydration).

### 4.2 Dispatch core (`apps/server/src/services/GmailDispatch.ts`, new)

```ts
export type GmailEventType = 'new_email' | 'labeled' | 'starred' | 'moved';
export async function dispatchGmailEvent(
  server: GmailServer,
  messageId: string,
  eventType: GmailEventType
): Promise<{ created: number; skipped: number }>;
```

Steps: construct `GmailService` from `server` credentials (same construction pattern as `GmailController`); hydrate (§4.3) — `null`/throw ⇒ propagate (caller decides 500 vs log, §4.1); load `gmailTrigger.findMany({ where: { serverId: server.id }, include: { zap: true } })`; per trigger, inside per-Zap try/catch (one bad Zap never blocks its siblings): skip if `!zap.isActive`; skip if existing `shouldTrigger(trigger, hydrated)` is false (function moves here unchanged, now fed real data — including `labels`, fixing B4's filter half); skip if dedup claim fails (D5); else `$transaction` create rows (D1/D9). When `GMAIL_EXECUTION_PATH=inline` (P2–P4 only), the per-Zap step instead calls the legacy executor — the _only_ place the switch is read.

Naming cleanup lands with it: both old `processGmailTrigger` functions are replaced by `dispatchGmailEvent` (+ `resolveGmailServersByEmail` for the webhook), and the unmounted `TriggerController.handleGmailTrigger` is deleted.

### 4.3 ZapRun payload contract (`ZapRun.metadata`) — the downstream API

Hydrated from `GmailService.getEmailMetadata` (`EmailMetadata`) + new `getEmailContent`. All dates ISO strings (JSON-safe). This shape is now a **public contract**: editor templates, filters, and future AI inputs bind to it — breaking changes require the same care as any trigger payload.

| Key                        | Type                                               | Source / notes                                                                                                                |
| -------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `id`, `messageId`          | string                                             | Gmail message id (both keys; `id` is the legacy key existing metadata may reference)                                          |
| `threadId`                 | string                                             |                                                                                                                               |
| `eventType`                | `'new_email' \| 'labeled' \| 'starred' \| 'moved'` | Existing `GmailTrigger.triggerType` vocabulary                                                                                |
| `from`                     | string                                             | `From` header                                                                                                                 |
| `to`                       | string[]                                           | `To` header split — downstream `{to}` stringifies comma-joined (existing `replaceKeys` behavior; document, don't change here) |
| `subject`                  | string                                             |                                                                                                                               |
| `snippet`                  | string                                             | Gmail snippet                                                                                                                 |
| `body`                     | string                                             | Plain-text body, ≤20,000 chars (D4)                                                                                           |
| `bodyTruncated`            | boolean                                            |                                                                                                                               |
| `labels`, `labelIds`       | string[]                                           | Same array under both keys (`labels` is what `shouldTrigger`/filters read; `labelIds` is Gmail's name)                        |
| `date`                     | string (ISO)                                       | `Date` header; `timestamp` (ISO, processing time) kept for legacy compat                                                      |
| `hasAttachments`, `isRead` | boolean                                            |                                                                                                                               |
| `serverId`                 | string                                             | Which connected mailbox produced this run (debugging/multi-mailbox routing; never credentials)                                |

Worked downstream uses once live: Telegram message `"📩 {from}: {subject}"`; filter `subject contains "invoice"`; AI step (PG consumer) `input: "{subject}\n\n{body}"`.

### 4.4 Push ingress repair (built only if push wins the D2 gate)

- **Auth:** replace `x-goog-signature`/HMAC with Pub/Sub **OIDC verification**: `Authorization: Bearer <JWT>` verified via `google-auth-library` (`OAuth2Client.verifyIdToken`) against `GMAIL_PUBSUB_AUDIENCE` (the push endpoint URL or configured audience) and expected push service-account email `GMAIL_PUBSUB_SERVICE_ACCOUNT`; fail closed 401 otherwise. If P1 discovers an external relay that _does_ send the current HMAC format, keep HMAC as a second accepted method behind its presence of header, with a dated removal TODO — otherwise delete `verifyGmailWebhookSignature` outright (nothing real depends on it).
- **History delta:** decode `{ emailAddress, historyId }` → resolve servers (D3; zero matches ⇒ log + 200, mailbox simply not connected — never 500-loop Pub/Sub) → per server: `GmailService.listHistory(lastHistoryId)` (new method over `users.history.list`, `historyTypes: ['messageAdded','labelAdded','labelRemoved']`); map records conservatively onto existing trigger vocabulary: `messagesAdded` → `new_email`; `labelsAdded` ∋ `STARRED` → `starred`, other label adds → `labeled`; `labelsRemoved` ∋ `INBOX` with a simultaneous add → `moved` (approximation documented; `shouldTrigger` still has final say via `watchedLabels`/metadata). Advance `lastHistoryId` to the notification's `historyId` **after** successful processing of that delta batch. Cursor `null` (first ever) ⇒ set to current `historyId`, process nothing (no mailbox-history flood). `history.list` 404 (cursor too old, standard Gmail semantics) ⇒ reset cursor the same way + warn.
- **Watch renewal:** `GET /api/cron/renew-gmail-watches` in `CronRoutes` (`CRON_SECRET` pattern, wired to the existing external cron): for each active server whose latest `GmailWatch.expiry` < 24 h out, `watchEmails(['INBOX'])`, write a new `GmailWatch` row, refresh `lastHistoryId` from the watch response. Without this, push silently dies every 7 days — it is in P3's acceptance, not a follow-up.
- `getProfile` email is stored at OAuth callback (`GmailController` already fetches `profile` at l.88 — persist `profile.data.emailAddress`).

### 4.5 Polling variant (built only if polling wins the D2 gate — sketched, not fully designed)

`GmailPoller extends BasePoller` in `apps/processor/src/pollers` (Sheets/Calendar precedent), polling each active server's inbox via `getNewEmails` since a stored cursor, converging on the same §4.3 payload + outbox writes that `BasePoller` already performs. Costs to weigh at the gate: `GmailService` currently lives in `apps/server` (the poller needs a Gmail client in `apps/processor` — extract shared code or duplicate a minimal client), only `new_email` semantics come naturally (labeled/starred need label-diffing state), but **zero GCP infrastructure** and latency identical to what outbox cadence already imposes. If chosen, flesh out in an addendum to this spec before building; §4.2/§4.3/G4–G6 are unaffected either way.

### 4.7 Last caller: legacy server webhook route

`POST /api/triggers/webhook/:zapId` (`TriggerController.handleWebhook` → `ZapController.processWebhookTrigger`) shares `executeZapActions`. P5 migrates it to the same two-write outbox enqueue (keeping its existing HMAC check and 200-response contract; signature-failure responses unchanged), after which `executeZapActions`, `processWebhookTrigger`, `processGmailTrigger` (ZapController), `ActionsController.executeAction` + `executeEmailAction`/`executeSolanaAction`/`replacePlaceholders`, the `GMAIL_EXECUTION_PATH` switch, and the now-unused nodemailer/SMTP execution block are **deleted**. (`env.ts` SMTP vars themselves stay only if something else reads them — verify at P5; the worker path uses Resend.) `GET /api/actions` (`fetchAvailableActions`) is untouched.

## 6. Test plan

**Unit — server** (jest, prisma mocks in `tests/setup.ts`; `GmailService` mocked at module boundary — **no test ever calls Google**):

1. `dispatchGmailEvent` happy path: hydrates once, creates exactly one `ZapRun (pending, §4.3 payload — assert key set incl. `subject/body/labels/date` ISO)` + one `ZapRunOutbox` inside a transaction, per matching active Zap.
2. Skips: `zap.isActive=false`; `shouldTrigger` false for each trigger type against hydrated fixtures (watched labels, sender filter, subject filter, starred via `labels: ['STARRED']` — the cases B4 made impossible).
3. Dedup: second identical `(zapId, messageId, eventType)` creates no rows; same message with different `eventType` does; Redis failure ⇒ proceeds + warns (fail-open pinned).
4. Resilience: one Zap's transaction throws ⇒ sibling Zap still gets rows; hydration `null` ⇒ **zero rows** and error propagates (caller 500 path); dedup claimed before a failing transaction ⇒ redispatch does not double-create for already-written Zaps.
5. Toggle: `GMAIL_EXECUTION_PATH=inline` routes to the legacy executor (spy), `outbox`/unset-after-P4 never imports it — deleted with the toggle in P5.
6. Webhook ingress (P3): valid OIDC ⇒ 200 + dispatch called; bad/missing JWT ⇒ 401, no dispatch; unknown `emailAddress` ⇒ 200 no-op; history mapping table-driven (`messagesAdded/labelsAdded[STARRED]/labelsAdded[X]/labelsRemoved[INBOX]` → `new_email/starred/labeled/moved`); cursor advances only after success; `history.list` 404 ⇒ cursor reset, no dispatch, 200.
7. Watch renewal (P3): renews only servers expiring <24 h, writes `GmailWatch`, refreshes `lastHistoryId`; refuses without `CRON_SECRET` (fail-closed, mirroring processor).
8. Scripts (P1/P4): audit is read-only (assert no write calls in default mode) and classifies Solana/`Gmail*`/`{{…}}` fixtures correctly; rewrite transforms only targeted Zaps' metadata, is idempotent, leaves `{already}` untouched; backfill sets email, skips failures, idempotent.
9. `run-status.test.ts` re-pinned (P5): webhook handlers return **200 and enqueue** (pending run + outbox) for a Zap whose action will fail in the worker; no run/outbox for missing-or-inactive Zap; handler does not throw on provider payloads.

**Unit — worker:** Email branch subjects resolve `{nested.key}` identically to body; literal subject without placeholders unchanged.

**E2E — gated** (`RUN_E2E=1`, real test Gmail account + staging DB/GCP, following `reports/trigger-testing-plan.md` harness style; never CI): send a real email → `ZapRun` appears `pending` → after processor/worker cycle, `completed`; a second action (`Webhook` to a request-catcher) receives `{subject}`/`{body}` and a chained `{previousOutput.…}` reference proving worker execution; replay the same Pub/Sub notification ⇒ still exactly one run; star the message ⇒ `starred` trigger fires a second run. If polling wins D2, same assertions driven by a poll cycle instead of a pushed notification.

## 8. Risks

- **P1 may reveal the push ingress "works" via an out-of-repo relay** (e.g., a Cloud Function enriching Pub/Sub into the current custom format + HMAC). Then B1/B2 are wrong _for production only_ — §4.4 shrinks to "keep dual auth, document the relay in-repo" and B3/B4 remain the real fixes. The spec is deliberately structured so this discovery only deletes work.
- **Gmail API quota:** hydration adds 1–2 API calls per message (+ `history.list` per notification). `GmailRateLimiter`/`GmailErrorHandler` already wrap `GmailService` calls; volume is bounded by actual mail to connected mailboxes. No batching in v1.
- **Body privacy/retention:** full text body (≤20k chars) now sits in `ZapRun.metadata` — the same place every other trigger payload already lives, no new retention class, but email bodies are more sensitive than webhook JSON. Q5 records owner acceptance; attachments and raw MIME are never stored.
- **`shouldTrigger` semantics drift:** fed real labels for the first time, `isLabeledTrigger`/`isMovedTrigger` read `metadata.targetLabels/targetFolder` keys whose editor provenance should be spot-checked in P2 tests against what the Gmail dashboard actually saves — a mismatch there is a pre-existing bug this spec surfaces, not one it must silently fix.
- **Outbox stranding:** a Zap deactivated between dispatch and drain leaves its outbox row unscanned-forever (processor filters `isActive`). Pre-existing for all outbox triggers; dispatch-side `isActive` check keeps Gmail from making it worse. Noted, not fixed here.
