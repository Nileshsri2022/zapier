Templates & Chaining — replaceKeys, previousOutput & Step Conditions

The glue between stages — what resolves, what stringifies, what skips.

Chaining Win: you can write a correct input template and a downstream reference that actually resolves. Primary source: replaceKeys.ts + worker/index.ts (steps)

Only input is templated — everything else is literal

From packages/ai/src/index.ts:55 and apps/worker/src/executeAiAction.ts:55:

// The single line that matters:
replaceKeys(config.input, runMetadata)   // runMetadata = { ...zapMetadata, stepOutputs, previousOutput }

// Inside replaceKeys (utils/replaceKeys.ts):
// Split on /{([^{}]+)}/g, walk obj via path.split(".").
// If leaf found → String(value); else keep "{placeholder}" literal.
// Unknown placeholder → stays literal, not empty string.

Consequences that surprise newcomers:

  • instructions is never template-resolved — it is owner configuration, not data.
  • categories / outputFields names/descriptions are literal — a {field} there stays as text.
  • Empty-ish resolution "" / " " → thrown as “AI step input resolved to empty text; check the input template” (index.ts:36).
  • resolvedInput.slice(0, policy.maxInputChars) — truncated tail flagged as truncated:true but still sent to provider.
Template hygiene
Map scalar leaves (strings/numbers): {text}, {subject}, {raw}, {previousOutput.fields.orderId}. Never map an entire object — String({…}) is "[object Object]" (next section).

What the AI step sees — the runMetadata map

At stage N, the AI call's replaceKeys merges:

{ ...zapMetadata, stepOutputs: { 1: envelope, 2: envelope, … }, previousOutput: stepOutputs[N-1] }
// zapMetadata itself contains trigger payload leaves, e.g.:
//   Webhook:        { raw, ticketId, message, … }
//   Gmail (PG):     { subject, snippet, body, from, to, messageId, … }   ← services/GmailDispatch.ts
//   WhatsApp:       { text, from, fromName, caption, … }                  ← apps/hooks/src/whatsappHandler.ts
//   Calendar/etc:   their own leaf sets (see Workflow Execution Gaps report)

Example — AI at stage 1 with input:"{subject}\n\n{snippet}" (Gmail) resolves to a single string: the subject line, two newlines, then the email snippet. That string becomes the framed user message: <input>…escaped…</input>.

Example — AI at stage 2 with input:"{previousOutput.fields.customerName} — {previousOutput.fields.issueType}" composes from stage 1’s validated envelope — you cannot inject raw unvalidated provider text into this path.

Downstream reads — two forms for two uses

After stage N succeeds, processMessage persists:

await client.zapRun.update({ data: { metadata: { ...zapMetadata, stepOutputs: {...stepOutputs, [N]: output } } } })
// output here is the AiStepOutput envelope { output, fields, provider, model, mode, usage, truncated, latencyMs }

The next stage resolves against it. Two accessors — for different string needs:

{previousOutput.output}                 // String — JSON.stringify(fields) when structured, else plain text
{previousOutput.fields.orderId}         // Leaf string (String(leaf))
{previousOutput.fields.amount}          // String(number) — because replaceKeys always String(value)
{stepOutputs.1.fields.category}         // Indexed — any prior stage, not just immediate predecessor
{stepOutputs.2.fields.email}            // Same pattern; stage numbers are stable, not array indices
The [object Object] trap — read carefully
replaceKeys does String(value). If you write {previousOutput.fields} you get "[object Object]" in your email/hook body. Use {previousOutput.output} if you need the whole validated JSON as a string, or a leaf path if you need a value. This is documented in spec §4.4 and surfaced in the editor hint: “Use scalar fields or serialized output, not a whole fields object.”

Step conditions — routing without branching code

Each action carries stepConditions: FilterCondition[]. Before stage N runs, the worker evaluates (apps/worker/src/index.ts:122):

conditionContext = { ...zapMetadata, previousOutput, stepOutputs }
if (!evaluateFilters(stepConditions, conditionContext)) {
  await advanceSkippedStage(N, lastStage, enqueueNext, markCompleted)
  // Logs "Skipping action N … step conditions not met" — run still completes successfully
}

Operators in evaluateFilters include equals, not_equals, contains, not_contains, greater_than, less_than, regex, is_empty — all compare via String(), so String(1499) === "1499" but 1499 === 1499 needs string coercion awareness.

Canonical use — ticket sentiment route: (spec §5.2)

// Stage 1: AI classify with categories ["positive","neutral","negative"]
// Stage 2: WhatsApp Send Message with:
stepConditions: [{ field:"previousOutput.fields.category", operator:"equals", value:"negative" }]
// → Negative tickets → WhatsApp alert. Non-negative → step skipped, run completes (no new branching code needed).

Other uses: previousOutput.fields.amount > "1000" via greater_than; previousOutput.fields.email contains "@example.com". Skipped stage still counts toward “completed” — it just did not do work (via skipStage.ts).

Your tangible win
Before saving an AI step, answer: “Can I name the exact placeholder my trigger guarantees?” If not, add a preceding filter/transform or pick a placeholder that truly exists. Then preview with a literal sample in the editor — that sample does not template-resolve (AiTestSchema, services/ai.ts:previewAi — sample sent as-is).
