Why one type for four providers?

Decision D1 in the spec: “Provider selection lives in metadata. The catalog exposes exactly one type.” That gives you:

  • No migration when you switch providers — Zap history and templates keep working; only metadata.provider changes.
  • Stronger invariants — exactly one seed (seed.ts:13 { type:"AI Transform", image:"/apps/ai.svg" }) must be worker-executable (KNOWN_ACTION_TYPES check in actions.test.ts:76). Four types would quadruple that audit surface.
  • Future-proofing for Puter/BYOK without a new catalog row per aggregator.

The allowlist dance — why “model not in allowlist” is not a bug

// platformModel() in config.ts:118 — the exact check at execution + save time:
model = config.model || env[`AI_DEFAULT_MODEL_${SUFFIX}`]
allowlist = env[`AI_MODEL_ALLOWLIST_${SUFFIX}`].split(",").map(trim).filter(Boolean)
if (!model || !allowlist.includes(model)) throw AiStepError("…allowlist")

// aiModels() for the editor — "configured" mirrors it:
configured = Boolean(env[key]) && models.length>0 && (!defaultModel || models.includes(defaultModel)) && (puter ? puterEnabled : true)

// For BYOK: model must simply be non-empty trimmed string, with an owned active connection + allowed host
if (provider==="openai_compatible") { connectionId required; model required non-empty bounded; connectionId forbidden for other providers }

Operator docs and services/ai.ts:validateAiMetadata repeat the same check on save (411), so you learn about a disallowed model before a Zap run does.

Puter — gated, not missing

Puter uses PUTER_AUTH_TOKEN via the Node SDK (docs.puter.com/getting-started → init(authToken) from @heyputer/puter.js/src/init.cjs), not browser login. The worker never opens a browser. From packages/ai/src/index.ts:49:

if (config.provider === 'puter' && !policy.puterEnabled) throw AiStepError('Puter is disabled pending provider verification')

The spec (§4.6) keeps AI_PUTER_ENABLED=false until five checks pass: server-side billing eligibility, token lifecycle/revocation, structured output & usage normalization, error→AiStepError mapping, and no automatic fallback. The code for Puter is shipped; the gate stays closed until verified. That is intentional — treat Puter as “code exists, operator disables”.

BYOK capability profiles — structured output is not free

A compatible endpoint may support any of three reviewed profiles (spec §4.5, packages/ai/src/providers.ts:chatBody):

  • chat_json_schema — strict response_format: { type:"json_schema", json_schema:{ name:"zapmate_ai_output", strict:true, schema } } (preferred)
  • chat_json_object — { type:"json_object" }
  • chat_prompt_json — no format hint; validated purely locally (the fallback)

You pick the profile in the connection dialog (AiMetaData.tsx:profiles); it controls what chatBody() sends. Spec §4.12 then adds the SSRF defenses: HTTPS-only 443, no IP literals/creds/query/fragment, exact-hostname allowlist (not suffix match), DNS A/AAAA validation, no redirects, bounded bytes/time — every runtime request, not just create.

What you’d see in the editor

AiMetaData.tsx flow:

  1. Fetch GET /api/actions/ai/models → providers + limits + default. Set provider = defaultProvider. Pre-select its default model.
  2. If compatible configured, fetch GET /api/ai/connections → render saved-connection picker + “+ New / Edit / Revoke / Test (billable)”.
  3. Choose Provider → model control swaps: platform = allowlist dropdown; compatible = free-text model ID.
  4. Choose Transformation → dynamic fields: categories (classify), OutputFields grid (extract / custom+fields), required-instructions hint (custom).
  5. “Test with sample input” → POST /api/actions/ai/test with literal sample (≤AI_MAX_INPUT_CHARS), billed, same budgets/provider path as worker. Render parsed fields + tokens + latency. “Save AI step” → validates against AiActionMetaDataSchema.
